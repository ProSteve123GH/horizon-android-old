## 1. Executive summary

- All Android-specific code is **fork-only**. Upstream `main` contains **no** `packaging/android/`, `crates/horizon-android/`, `crates/horizon-client/src/android/`, Android JNI bridge, touch input glue, voice chat or vendored Android winit backend. Of 7,233 fork files vs 11,691 upstream files, 5,312 are common and 2,327 of those differ (upstream drift). The migration therefore cannot "rebase Android on top of 26.4" by merging alone: every fork-only piece must be **carried forward explicitly**, and the ~35 shared files that contain Android hooks must be **reconciled by hand**.
- The single largest structural risk is that **upstream relocated gameplay into subdirectories** (`game/interface/…`, `game/runtime/…`, generated `game_modules.rs`) while the fork still uses a flat `game/*.rs` module list. The recently fixed mouse-capture bridge lives in the fork's old-path `game/pointer_capture.rs`; upstream's equivalent is `game/interface/pointer_capture.rs` and has no Android fix. The same applies to `game/window_handler.rs` → `game/runtime/window_handler.rs` and `game/ime.rs` → `game/interface/ime.rs`.
- The microphone permission hook (commit for `fix/android-voicechat-deps` branch) is confined to `AndroidManifest.xml` + `android/platform.rs` + `game/voicechat.rs`; it is self-contained but depends on shared build/crate files owned by the coordinator.
- Version-dependent Android references are mostly derived (`horizon_core::VANILLA_VERSION` in the bridge snapshot), but there are **hardcoded "Minecraft 26.3" user-facing strings and CI step names** that must be updated, plus the `research-lock.json` pin used by `tools/android_prepare.py`.

## 3. Upstream comparison — what 26.4 work can break Android

1. **Gameplay module relocation (highest risk).** Upstream `crates/horizon-client/src/game.rs` uses `include!(concat!(env!("OUT_DIR"), "/game_modules.rs"))` and delegates to `game/interface/`, `game/runtime/`, `game/world/`, `game/host/`, `game/modding/`, `game/entities/`, `game/blocks/`, `game/items/`, `game/mobs/`, `game/administration/`, `game/network/`, `game/native_hooks/`. The fork has a flat `game/*.rs` list. Android hooks in `game.rs` (~30 `cfg(target_os="android")` sites), `game/window_handler.rs`, `game/pointer_capture.rs`, `game/ime.rs`, `game/android_input.rs`, `game/voicechat.rs`, `game/android_bundled.rs` must be transplanted, not merged mechanically.
2. **Rendering/Vulkan.** The 26.4 migration's new default Vulkan backend and any new pipelines/features touch `gfx.rs` and `gfx/*` (`arena.rs`, `flat.rs`, `hdr.rs`, `output_apply.rs`, `panorama.rs`, `surface_setup.rs`, `cull/`, `gpu_culling/`). Android-specific gates that must survive: opaque/cutout no-discard pipelines, `late_sky` ordering guard, `graphics_startup` recovery marker, non-conformant adapter retry, `compatibility()` feature trimming, atlas limit, cache budgets, `renderer.info` fields used by the diagnostics snapshot. **Do not assume desktop Vulkan support implies Android Vulkan support** (driver differences, swapchain behavior, feature limits). Agent 4 must validate on device via CI.
3. **Shared launcher sources.** `android_main.rs` compiles nine `launcher/src/*.rs` files by `#[path]`. Upstream changes to `launcher/src/account.rs`, `browser.rs`, `worlds.rs`, `proxy.rs`, `server_list.rs`, `skins.rs`, `i18n.rs`, `native_fit.rs`, `native_status.rs` (and their new submodules, e.g. `account/session.rs`, `browser/horizon.rs`, `browser/installed.rs`) can break the cdylib build. Note: the cdylib declares local `nightly`/`github_mods` shims and a `backend` module to satisfy those shared sources; those shims may need updating.
4. **Touch implementation.** `touch.rs` and `touch/layout.rs` are shared with upstream and differ. If upstream 26.4 changes touch settings keys, `Control` enum size, or `Settings` serialization, then `touch_layouts.rs` (`CONTROLS = 14`, `MODES`, merge/apply functions), `bridge.rs::touch_snapshot`, `TouchLayouts.kt`, `TouchEditor.kt` and `bedrock-controls.json` must be updated together. The default file name `horizon-touch.json` and profile store must stay stable.
5. **Version-dependent Android data.** `research-lock.json` pins 26.3 manifest/jar/library/asset SHA-1s; `tools/android_prepare.py` refuses other versions. `PlayScreen.kt` and `minecraft_import.rs` contain literal 26.3 strings; `dev-builds.yml` step names mention 26.3. The bridge's `minecraft` field auto-follows `horizon_core::VANILLA_VERSION`, so that constant is the single source of truth for the UI.
6. **Mod-removal overlap (classification, not decided here).** `android/native_mods.rs` + `NativeMods.java/.kt` + `android/catalog.rs` implement native-mod import/compile through `horizon-mods`; `game/android_bundled.rs` is a **fixed MIT-licensed bundle** (zoom, minimap, recipes, smartf3) with no downloaded code — an independent Horizon/Android feature, not general mod loading. Agent 7 must classify these explicitly; the task's preservation rule says preserve independent features while removing general loaders.
7. **winit / wgpu-hal.** The fork vendors `third_party/winit` (upstream has none) with Android mouse/key/touch handling and `third_party/wgpu-hal` (present upstream, no Android-specific delta). An upstream winit/wgpu upgrade must not silently replace the fork's `mouse_state.rs`, `platform_impl/android/mod.rs` relative-motion path or the `winit = { path = … }` / `wgpu-hal = { path = … }` overrides in root `Cargo.toml`.
8. **Audio/voice.** `game/voicechat.rs` and `crates/voicechat-engine/` are fork-only and depend on `audio::set_output_tap` in the shared `audio.rs`. Upstream audio refactors in 26.4 can break that tap; coordinate with Agent 6 and Agent 4.

## 6. Risks and open questions

- **Critical:** 26.4's gameplay restructure means an upstream-style "take the new `game.rs`" will drop every Android hook unless explicitly re-applied. This is the main place where Android functionality could be silently lost. A file-by-file diff of fork `game.rs`/`window_handler.rs`/`pointer_capture.rs` against upstream's relocated equivalents should be produced before integration.
- **Critical:** the mouse-capture fix is a 36-line patch in a fork-only file that does not exist at that path upstream. If the integrator copies upstream `game/interface/pointer_capture.rs`, camera look on physical mice breaks again (exactly the bug fixed by `d766ec5f7f`).
- **High:** microphone permission works through `requestPermissions` with no result callback; behavior on Android 13+ (runtime permission) and on denial is unverified. The engine retries on next mic open, so UX may be a silent no-op. Confirm with Agent 6/QA.
- **High:** 26.4 default Vulkan backend may request features not available on older Android drivers; the fork's `compatibility()` path and GLES fallback must be re-checked, not assumed. Android startup recovery marker must be preserved to avoid a stuck black screen after a driver crash.
- **Medium:** version strings are duplicated (Kotlin literals, workflow step names, `research-lock.json`, comments). A partial update leaves misleading UI or a prepare step that refuses the new snapshot.
- **Medium:** `NativeBridge.kt` comments say "Minecraft 26.3" and the app version is `0.7.7`; decide whether `backend::VERSION`/Gradle `versionName` need bumping for the 26.4 release — coordinator's call.
- **Medium:** `docs/android-upstream.json` records a review of nightly-source `2026-11-13-9f42064` and states that some ABIs and final APKs still need validation. Treat all prior "passed" claims there as historical, not as 26.4 evidence.
- **Low:** `BEDROCK_TODO` remains unimplemented (Bedrock controls JSON import is detected, not converted); no change required for 26.4 unless the task wants it.
- **Storage constraint:** per `LOCAL_ENVIRONMENT.md` the agent workspace has ~700 MB RAM and ~10 GB storage with ~3 GB used; no additional downloads/builds were performed for this inventory.
