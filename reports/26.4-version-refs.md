Read-only survey of fork `ProSteve123GH/horizon-android-old`, branch `dev/26.4`, against

## 0. How version truth flows (read this first)

Two authoritative sources, everything else follows:

1. `research-lock.json` → `minecraft.version` is read by `tools/lab.py:31-43` (`pinned_version`,
   `GAME`, `RESOURCES`). Every Python tool that uses `lab.*` follows the pin automatically.
   `lab.py:46-50` reads the client jar's own `version.json` for facts.
2. `crates/horizon-core/src/version.rs` is **generated** by `tools/gen_version_consts.py`
   (header at line 2: "Generated by tools/gen_version_consts.py; do not edit by hand").
   It renders `VERSION_ID`, `VANILLA_VERSION`, `PROTOCOL_VERSION`, `DATA_VERSION`,
   `RESOURCE_PACK_FORMAT`, `DATA_PACK_FORMAT`, `JAVA_VERSION`, `STABLE`, `BUILD_TIME`
   from `lab.version_info()`. `tools/port_regen.py:255-267` lists it as generator `version_consts`.

Correct order of work: update the pin (`research-lock.json`) → obtain/verify the official
`26.4-snapshot-10` jars → regenerate `version.rs` (and the other generated tables) → then fix
the hand-maintained literals below. Never hand-edit a generated file.

`docs/version-ports.md:28-35` states that every Rust site reads these constants, and — importantly —
that "test fixtures that state a version (a level.dat to read, a relay message) keep their literals:
they test parsing, not the pin." That is the rule used for the KEEP list in §5.

Snapshot caveat: `docs/version-ports.md:108-109` says snapshots are only prepared/diffed/reported
(`port --snapshot`), and `:196` says `port NEW` runs `regen` after `diff` with `--no-regen` for
snapshots. `tools/port_regen.py` itself does not obviously reject a snapshot id
(`pinned_lock` at `:57-72` just copies `manifest["id"]`, which can be `26.4-snapshot-10`).
Whoever runs the pipeline must force the regen stage for the exact snapshot (or run the six
generators directly) and record that deviation, per TASK §3. `version_port.py detect --snapshots`
is only a detector; do not substitute 26.4 release.

## 6. Risks / notes for the coordinator

- **Do not invent the snapshot's numbers.** 777/5023/(97,1)/(121,0)/25 and the build time are 26.3
  facts. Take every value from the official `26.4-snapshot-10` version JSON and jars, verify SHA-1s,
  then regenerate. `STABLE` must flip to `false`.
- `mc_version("26.4-snapshot-10")` = **260400** by the documented rule (parsing stops at the first
  non-digit), so shader-pack `MC_VERSION` changes from 260300; no code change needed, only the test.
- `MINECRAFT_VERSION = "26.4-snapshot-10"` in Polytone parses as `[26,4,0,10]`; verify pack
  conditions that use exact equality or upper bounds (e.g. `[26.2,26.3]`) still behave as intended.
- The Kotlin launcher currently hardcodes user-visible "Minecraft 26.3" strings; those five sites
  (§3) are the only Android UI version references. Prefer replacing with a resource/derived value
  to satisfy AGENTS.md's translation-ready rule.
- The 198 hardcoded `.local/.../26.3` paths (§4) are the largest breakage class. Convert them to
  `lab.RESOURCES`/`VANILLA_VERSION` in one pass rather than literal-replacing, or they will break
