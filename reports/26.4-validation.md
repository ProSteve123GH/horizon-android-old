## 0. Executive summary (findings that change the plan)

1. **The fork has exactly two active workflows**, both under `.github/workflows/`:
   `android-dev.yml` (workflow ID `410801034`) and `android-source.yml` (ID `410801035`).
   The ~50 other workflows visible from a bare `gh workflow list` in this workspace belong to
   **upstream `horizon-rust/horizon`**, not the fork — `gh` resolves the `upstream` git remote
   here. **Every `gh` command in this report passes `-R ProSteve123GH/horizon-android-old`
   explicitly.** On the fork, `git ls-remote --symref origin HEAD` → `android` (default branch).
2. **Neither workflow triggers automatically on `dev/26.4`.** `android-dev.yml` push branches are
   `android`, `android-dev*`, `dev/android-*`; `android-source.yml` push/PR base is only `android`.
   `dev/26.4` matches none of them. All validation of this branch must be started with
   **`workflow_dispatch`** with `--ref dev/26.4`.
3. **`dev/26.4` is not on the remote yet** (`git ls-remote --heads origin refs/heads/dev/26.4`
   returned nothing). The coordinator must push the branch before any dispatch; `gh workflow run
   --ref dev/26.4` cannot target a non-existent remote ref.
4. **`android-dev.yml` can produce a signed dev APK from `dev/26.4` via dispatch.** Its build job
   `if:` includes `github.event_name == 'workflow_dispatch'`, which overrides the branch-name
   check. Inputs: `profile` (`release`/`fast`) and `all_abis` (bool). Signing secret
   `ANDROID_DEV_KEYSTORE_BASE64` exists in the fork (API-verified by name only).
5. **"Source checks" are not lightweight.** Every `test_android_*.py` invoked by
   `android-source.yml`'s `source` job shells out to `cargo test`/`cargo run`. The only
   Rust-free part is `git diff --check`, `check_public_tree.py --history`, the `tests/test_android*.py`
   unittest subset, and the two `cmp` export checks. The optional `native` job is a 4-ABI
   `cargo check` matrix.
6. **Both fork workflows are currently healthy on `android`** (latest API-observed runs:
   `android-dev` run `44839627665` success, `android-source` run `44839627375` success,
   2026-11-20). This is baseline evidence only; it says nothing about `dev/26.4`.
7. **Runtime validation is impossible in the available CI.** There is no device-testing workflow
   and no SVC server. Touch, Vulkan init, audio, mic, UDP voice chat, and world startup must be
   labelled NOT TESTED / BLOCKED until done on a physical device.

## 2. `android-dev.yml` signed dev APK — detailed answer

**Yes, it can produce a signed dev APK from `dev/26.4` via `workflow_dispatch`.**

- **Inputs:** `profile` = `release` (default) or `fast`; `all_abis` = `false` (default,
  `arm64-v8a` only) or `true` (adds `armeabi-v7a`, `x86`, `x86_64`). For the acceptance criteria
  use `release` + `all_abis=false` (ARM64 is the required target). Use `fast` only for quicker
  iteration builds.
- **Signing:** step "Select the repository dev key or fallback signing key" uses secret
  `ANDROID_DEV_KEYSTORE_BASE64` (API-confirmed present) → `source=repository secret`; otherwise a
  cached dev key, otherwise a freshly generated `androiddebugkey` (RSA, 10 000 days, CN=Horizon
  Android Dev CI) cached under `horizon-dev-signing-v1`. Signing material is removed in an
  `if: always()` step. **Honest wording:** this is a *dev/debug-signed* APK. The workflow's own
  release notes say "Not signed for distribution; install only if you trust the branch." Do not
  call it a distribution-signed release.
- **Artifact:** `actions/upload-artifact` name `horizon-dev-${{ github.run_number }}-${{ matrix.abi }}`
  (e.g. `horizon-dev-123-arm64-v8a`), containing `dist/`: the versioned APK
  `Horizon-Android-dev.<run>.<sha12>-<abi>.apk`, `SHA256SUMS.txt`, `BUILD.json`,
  `LICENSE.txt`, `THIRD_PARTY_NOTICES.md`; retention 14 days.
- **Release asset:** `gh release upload dev-latest --clobber` to the pre-existing/auto-created
  prerelease `dev-latest`, with stable names `Horizon-Android-dev-<abi>.apk` (plus BUILD.json,
  notices, checksums). The stable asset name is overwritten on every build; the run artifact is
  the immutable per-run copy.
- **APK identity / metadata:** package `dev.horizon.android.steve.dev`, `experimental: true`,
  `version_code = 1000 + GITHUB_RUN_NUMBER`, dev build version
  `<run>.${GITHUB_SHA:0:12}`. `aapt2 dump badging` output is printed to the log. These are
  recorded in `BUILD.json` together with `commit`, `branch`, `abi`, `profile`, `signing`,
  `built_at`, and a `workflow_run` URL — use them as the provenance evidence in the report.
- **In-workflow audits:** `python3 tools/check_public_tree.py` and
  `python3 -m unittest discover -s tests -p 'test_android_release_audit.py'` run before the build;
  `tools/check_android_release.py` / `aapt2` validate the built APK. These are the only
  APK-side checks that exist today.

Download an artifact for read-only inspection (watch the ~3 GB/10 GB local storage budget; use
`du -x`, never `df -h`, and a scratch dir such as `/tmp/opencode/26.4-apk`):

```sh
mkdir -p /tmp/opencode/26.4-apk
gh run download <run-id> -R ProSteve123GH/horizon-android-old \
  -n horizon-dev-<run-number>-arm64-v8a -D /tmp/opencode/26.4-apk
du -x -h --max-depth=1 /tmp/opencode/26.4-apk
sha256sum -c /tmp/opencode/26.4-apk/SHA256SUMS.txt
python3 -c 'import json;print(json.load(open("/tmp/opencode/26.4-apk/BUILD.json")))'
# Inspect packaged native libs without building anything (if unzip is available):
unzip -l /tmp/opencode/26.4-apk/*.apk | grep -E 'lib/arm64-v8a/|classes.*dex'
```

### Stage 6 — Rust unit tests, clippy, rustfmt, parity (blocked on this branch)

No active workflow on the fork runs them, and local execution is forbidden. Options for the
coordinator, in order of preference:

### Sequencing and cancellation

- Run Stage 1 → Stage 2 → Stage 3 serially. Stages 1 and 2 share concurrency group
  `android-checks-...` on the same ref; Stage 3 uses `android-dev-${{ github.ref }}`. Launching a
  second run on the same ref before the first finishes cancels the first
  (`cancel-in-progress: true`).
- Use `-f profile=fast` for a quick first APK; the **final** gate must be `release`.

## 5. Honest reporting framework

Use exactly the `TASK.md` §8 labels:

| Label | Meaning (apply strictly) |
|---|---|
| PASS | Command actually executed on `dev/26.4` and succeeded; evidence (run URL, step log, artifact, SHA) attached. |
| PARTIAL | Only part of the feature was exercised (e.g. APK builds but device runtime not tested). |
| BLOCKED | Blocker documented: no device, no SVC server, no 26.4 server, or no CI job for Rust/parity. |
| FAIL | Command executed and failed; include the failing step and log excerpt, do not hide it. |
| NOT TESTED | No validation performed; never upgrade to PASS because code "looks right" or "compiles". |
| N/A | Criterion does not apply (e.g. x86 ABI when only ARM64 is required) — use sparingly and justify. |

Rules: **compiles ≠ works**. A green `android-build` step never upgrades "Application starts",
"Vulkan initialized", "Touch controls", "Audio", or "Voice chat" above NOT TESTED. Always cite
the exact commit SHA and run ID. Paste CI Markdown summaries rather than paraphrasing.

## 6. Risks and caveats the coordinator must handle

- **R1 — 26.3-labelled build inputs (highest risk to validation honesty).** `android-dev.yml` still
  says "Set up JDK 25 for Minecraft 26.3 exporters", "Restore prepared Minecraft 26.3 engine
  inputs", with cache key `android-minecraft-${{ hashFiles('research-lock.json', ...) }}` and
  `restore-keys: android-minecraft-`. If `research-lock.json` is updated for 26.4, the primary key
  changes, but the broad fallback can restore **stale 26.3 prepared inputs**; `android_prepare.py`
  runs unconditionally afterwards, so verify in the Stage 3 log that it actually prepares
  `26.4-snapshot-10`. Add an explicit assertion (version string in prepared output / `BUILD.json`)
  before claiming the APK runs 26.4. A green build against 26.3 inputs would be a **false PASS**.
- **R2 — workflow edits break a byte-exact contract.** `tests/test_android_ci_contract.py` and
  `android-source.yml`'s `cmp` steps require
  `.github/workflows/android-dev.yml == packaging/android/dev-builds.yml` and
  `.github/workflows/android-source.yml == packaging/android/source-checks.yml`, and pin specific
  action SHAs. If Stage 6 requires a new CI job, copy the edited file to its packaged export
  byte-for-byte and keep the pinned SHAs; re-run Stage 1.
- **R3 — `gh` repo resolution.** In this workspace `gh` resolves `horizon-rust/horizon` (because a
  `remote.upstream` exists). A bare `gh workflow run ...` would dispatch the **upstream** repo.
  Always pass `-R ProSteve123GH/horizon-android-old` (or `--repo`).
- **R4 — remote ref must exist.** `dev/26.4` is currently local-only; push first. Never force-push.
- **R5 — dispatch does not need a PR**, but opening a PR into `android` would trigger
  `android-source.yml` on the PR merge ref and `android-dev.yml` would skip the build job (its
  `if:` excludes PRs). Since the task says no PR, use dispatch only.
- **R6 — signing semantics.** "Signed dev APK" = dev/debug key; the `dev-latest` release notes
  explicitly disclaim distribution signing. Report it as such.
- **R7 — concurrency.** Two dispatches on the same ref cancel each other; wait for each run to
  finish.
- **R8 — local storage.** ~3 GB/10 GB used; keep downloads in a scratch dir, use `du -x`, never
  `df -h`, and do not retain multiple APKs/exports.

```sh
REF=dev/26.4

# Precondition
git ls-remote --heads origin refs/heads/$REF

# Stage 1 — source checks + host Rust harnesses
gh workflow run android-source.yml -R $REPO --ref $REF -F native_checks=false

# Stage 2 — 4-ABI cargo check
gh workflow run android-source.yml -R $REPO --ref $REF -F native_checks=true

# Stage 3 — signed dev APK (final gate uses release)
gh workflow run android-dev.yml -R $REPO --ref $REF -f profile=release -F all_abis=false

# Observe
gh run list -R $REPO --workflow=android-dev.yml --branch=$REF --limit 3
gh run watch <run-id> -R $REPO --exit-status
gh run view <run-id> -R $REPO --log-failed

# Artifact (read-only inspection; scratch dir, mind 10 GB ceiling)
gh run download <run-id> -R $REPO -n horizon-dev-<run-number>-arm64-v8a -D /tmp/opencode/26.4-apk
sha256sum -c /tmp/opencode/26.4-apk/SHA256SUMS.txt
```

**Bottom line:** with a pushed `dev/26.4`, CI can prove repository hygiene, Android-side harness
behavior, 4-ABI type-checking, and production of a dev-signed ARM64 APK with provenance. It
cannot prove the game starts, that touch/Vulkan/audio/SVC work, that the APK actually contains
26.4-snapshot-10 data (unless R1 is explicitly checked), or that Rust unit/parity tests pass
(no CI job on this branch). Label those accordingly and do not claim completion on a green build.

## 9. CI-only table regeneration

`.github/workflows/port-regen.yml` is a dispatch-only workflow (no PR) that:
1. checks out the dispatched branch,
2. sets up JDK 25,
3. runs `python3 tools/android_prepare.py` (the same prepare stage as the APK build),
4. regenerates `crates/horizon-protocol/src/ids.rs` from `.local/datagen/out/reports/packets.json`,
5. commits the regenerated table back to the branch and pushes it.

Invoke it with:

```sh
gh workflow run port-regen.yml -R ProSteve123GH/horizon-android-old --ref dev/26.4
```

Run this only after the Java exporters compile, then rebuild the APK. Regeneration is enabled for
packet ids because these are protocol facts from vanilla's own data generator; the remaining
